01
A User-Centred Design ProcessISO 9241-210 applied to a business case




An interface is not designed for its own sake but for specified users pursuing specified goals in a specified context. The standard ISO 9241-210 describes an iterative, human-centred process in four activities:




Understand the context of useWho are the users, what are their tasks, environment and constraints?


Specify requirementsTranslate needs into functional, usability and accessibility requirements.


Produce design solutionsSketches, prototypes, then the implemented interface.


Evaluate against requirementsHeuristic review, accessibility audit, tests with users; then iterate.








Project brief: Tipaza Cash-Flow


Context. Owners of very small enterprises in the Tipaza region (shops, workshops, service providers) track their receipts and expenses in paper notebooks. They lack a quick view of their balance and of where the money goes. They mostly use a smartphone, sometimes a shared office computer; their digital literacy varies.




User storyAcceptance criterion


As an owner, I want to record a receipt or an expense in a few seconds.A single form, at most five fields, valid with the keyboard alone; confirmation announced.


As an owner, I want to see my current balance at a glance.Income, expenses and balance always visible and updated immediately.


As an owner, I want to know which categories cost me the most.A chart of expenses by category, with a text alternative.


As an owner, I want to find and correct a transaction.Filter by type and search by description; deletion possible.


As an owner, I want to give my figures to my accountant.Export of the transactions as a CSV file readable by a spreadsheet.


As an owner, I do not want to lose my data when I close the browser.Automatic local persistence.




Non-functional requirementsResponsive from 320px; usable in dark environments; WCAG 2.2 level AA; no external library; amounts formatted in Algerian dinars; no data sent to any server.







02
Application ArchitectureState, logic, view and controllers




Small applications quickly become unmaintainable when every handler modifies the page directly. We adopt a unidirectional data flow: the application has a single state object; event handlers only modify that state; a render() function then derives the entire view from it. The state is the single source of truth; the DOM is merely its projection.


Unidirectional data flow




LayerResponsibilityIn the project


DataState and persistencestate, load(), save()


LogicPure computations, testable without a pagetotals(), expensesByCategory(), toCSV()


ViewRendering the state into the DOMrenderKpis(), renderTable(), renderChart()


ControllersTranslating events into state changesForm submission, delegated deletion, filters, theme, export




A conceptual linkThis is the same principle that underlies modern front-end frameworks (React, Vue, Svelte): view = f(state). Implementing it by hand in plain JavaScript is the best way to understand those frameworks later.







03
Step 1: Semantic StructureHTML




The markup is written first, without any style, following Sessions 01-04: landmarks, a heading hierarchy, a labelled form with a fieldset for the transaction type, a data table with a caption, a chart with an accessible name and description, and a live region for announcements.









04
Step 2: Design System and LayoutCSS




The stylesheet starts with design tokens (Session 05), redefined for the dark theme; the layout uses Grid with template areas and a mobile-first breakpoint (Sessions 06-07); interactions receive short transitions, and motion is removed under reduced-motion preferences (Session 08).









05
Step 3: State, Logic and PersistenceJavaScript, data and logic layers




Amounts are stored as numbers and formatted only at render time; dates as ISO strings (YYYY-MM-DD), which sort correctly as text. Every computation is a pure function over the array of transactions (Session 10), and storage access is protected by try...catch.









06
Step 4: Rendering and ControllersJavaScript, view and events




Rendering uses textContent exclusively for user data (Session 11), the chart is generated as SVG elements with createElementNS, and a single delegated listener handles all deletion buttons. The CSV export builds a Blob and triggers a download through a temporary link.









07
The Complete ApplicationRun it, use it, break it




The four steps assembled into a single file. Add income and expenses, filter, delete, switch the theme, export the CSV, then reload the preview: the data persist. Use Edit live to experiment with the code.









08
Evaluation, Testing and DeploymentHeuristics, accessibility, quality




Heuristic evaluation


Jakob Nielsen's ten heuristics are general principles for interaction design. Evaluate the application above and tick each heuristic you consider satisfied; the score updates automatically. In practice, three to five independent evaluators find most of the usability problems.

DeploymentA static application (HTML, CSS, JS only) can be published free of charge on GitHub Pages or Netlify: create a repository, push the files with index.html at the root, and enable Pages. The site is then served over HTTPS at a public address, ready for user testing.







09
Practical ExercisesExtend the application


Each exercise extends the complete application of section 07. Copy it into your editor, or use Edit live, and integrate the code of the solution in the indicated place.


EX 01
Category budget alerts
Foundational


Define a monthly budget for each expense category (for example Rent 40 000, Supplies 15 000 DZD). In the chart, colour in red the bars of categories whose total exceeds their budget, and add the text "over budget" to their label, so that the information does not rely on colour alone (WCAG 1.4.1).




IntegrationAdd the BUDGETS constant to the data layer and replace the bar-creation part of renderChart(); add the CSS class .bar.over { fill: #dc2626; }.




EX 02
Sortable table columns
Intermediate


Make the Date and Amount column headers sortable: each header contains a button; activating it sorts ascending, then descending on the next activation. Store the sort key and direction in the state, and reflect the current order with aria-sort on the th elements.






EX 03
Monthly period filter
Intermediate


Add an input type="month" to choose the period. KPIs, table and chart must all reflect only the transactions of the selected month, with an "All periods" option. Explain why this change requires modifying a single function in our architecture.




Why one function?All views derive from the state through visibleTransactions(). Filtering there propagates the period to the KPIs, the table and the chart automatically: the benefit of deriving the view from a single source of truth.




EX 04
Undoable deletion
Advanced


Following heuristic 3, replace immediate deletion with an undoable one: after deletion, a toast "Transaction deleted. Undo" appears for six seconds; activating Undo restores the transaction at its original position. The toast must be announced to screen readers, its button must receive the focus, and pressing Escape must close it.

Final ProjectTeam work, assessed by deliverables and an oral defence




Design and build a business interface


In teams of two or three, design and develop a complete single-page application addressing a real need of an Algerian organisation, following the process and architecture of this session. Suggested subjects: appointment booking for a clinic, stock management for a pharmacy, a tutoring marketplace for the faculty, a micro-credit simulator, an event registration system, or a subject of your choice approved by the lecturer.


    

  • Analysis (week 1): context of use, two personas, at least eight user stories with acceptance criteria.
    • 

  • Design (week 2): paper or digital wireframes for mobile and desktop, and the design tokens.
    • 

  • Implementation (weeks 3-4): semantic HTML, a responsive CSS design system, and a state-driven JavaScript architecture with persistence; no framework or library.
    • 

  • Evaluation (week 5): a heuristic evaluation by another team, a WCAG audit, Lighthouse reports, and the corrections made.
    • 

  • Deliverables: the source code in a Git repository, the deployed URL, a report of 8 to 12 pages, and a 10-minute oral defence with a live demonstration.
