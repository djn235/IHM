01
The Form Submission Modelform, action, method, name and value




A form collects user input and, on submission, serialises every successful control into a sequence of name=value pairs sent to the URL in action using the HTTP method. A control without a name attribute is never submitted, however carefully the user filled it in.




GETPOST


Location of the dataAppended to the URL as a query stringIn the request body


VisibilityVisible, logged by servers and proxies, stored in historyNot in the URL; encrypted under HTTPS


SemanticsSafe, idempotent retrieval (search, filters)Actions that change state (registration, payment)


SizeLimited by URL lengthPractically unlimited; required for file uploads with enctype="multipart/form-data"

ObserveWith GET, the password appears in clear text in the URL. Note also that the unnamed checkbox is absent from the payload, and that an unchecked checkbox sends nothing at all.







02
Labels and Groupinglabel, fieldset and legend




Every control requires an accessible name. The label element provides it and, in addition, enlarges the clickable area: activating the label focuses or toggles its control, which is valuable on touch screens and for users with motor impairments.




Explicit association
label for="x" refers to the control's id="x". The most robust technique.


Implicit association
The control is nested inside its label. Valid, but less well supported by some assistive technologies.




fieldset groups semantically related controls, and its first child legend captions the group. Screen readers announce the legend before each control, which is indispensable for radio buttons ("Delivery mode: Express").






Placeholder is not a labelThe placeholder text vanishes as soon as the user types, often has insufficient contrast, and is inconsistently exposed to assistive technologies. Use it only for a format hint, in addition to a visible label.





03
HTML5 Controlsinput types, select, textarea, datalist and button




HTML5 introduced specialised input types. Each brings native semantics, built-in validation and, on mobile devices, an adapted virtual keyboard.




TypeBehaviourBusiness example


emailValidates address syntax; "@" keyboardCustomer contact


telNumeric keypad; no implicit validationMobile number


numberSpinner; min, max, stepOrder quantity


rangeSlider for imprecise valuesLoan duration


date, time, monthNative pickers; ISO value formatDelivery date


url, search, color, fileSpecialised entry and pickersCompany website, logo upload


checkbox / radioMultiple choices / one choice among a group sharing the same nameOptions / payment method








select versus datalistselect restricts the user to the listed options. datalist, linked through the list attribute, merely suggests values while allowing free entry: appropriate for a city field with an open set of answers.





04
Native Constraint Validationrequired, pattern, min, max, length




The browser can verify input before submission, displaying localised error messages and blocking invalid data, without a single line of JavaScript. This client-side validation improves the experience but never replaces server-side validation, since any HTTP client can bypass it.




AttributeConstraint


requiredA value must be provided


minlength / maxlengthBounds on the number of characters


min / max / stepNumeric or date bounds and granularity


patternA regular expression the entire value must match


typeSyntax checks for email and url


novalidate (on form)Disables native validation (when JavaScript handles it)




autocomplete tokens (name, email, tel, postal-code, new-password...) enable reliable autofill and satisfy WCAG 1.3.5. inputmode selects the virtual keyboard independently of the type.






Reading the regular expressionpattern="0[5-7][0-9]{8}" requires a 0, then a 5, 6 or 7, then exactly eight digits: the format of an Algerian mobile number. The pattern is implicitly anchored at both ends, so the whole value must match.





05
Accessibility and ARIAWCAG principles applied to forms




The Web Content Accessibility Guidelines organise their requirements around four principles, summarised by the acronym POUR:




PPerceivable
Labels, text alternatives, sufficient contrast.


OOperable
Full keyboard operability, visible focus, no traps.


UUnderstandable
Instructions, clear error identification and suggestions.


RRobust
Valid markup exposing name, role and value.








ARIA: Accessible Rich Internet Applications


ARIA attributes supplement native semantics when HTML alone is insufficient. The first rule of ARIA is to avoid it whenever a native element provides the required semantics: a button is always preferable to div role="button".


    

  • aria-describedby links a control to help or error text, which is read after the label.
    • 

  • aria-invalid="true" signals an invalid value.
    • 

  • aria-live="polite" announces dynamic messages (e.g. an error summary) without moving focus.
    • 

  • aria-current="page" marks the current item in a navigation set.
    • 







Keyboard testUnplug the mouse and complete the form using only Tab, Shift+Tab, Space, the arrow keys and Enter. If any step is impossible, or if the focus position is ever invisible, the form fails WCAG 2.1.1 and 2.4.7.





06
Practical ExercisesDesign, validate, audit


EX 01
Student registration form
Foundational


Create a registration form for the faculty's digital platform, sent by POST to /register, containing: last name and first name, student number, e-mail, date of birth, programme (select), study year (radio buttons in a fieldset), a password, acceptance of the rules (checkbox) and a submit button. Every control must be labelled and named.






EX 02
Online order form
Intermediate


Design the checkout form of an e-shop, structured in three fieldset groups:


  • Product: a product select with two optgroup categories, quantity from 1 to 10.
  • Delivery: wilaya with a datalist of suggestions, address in a textarea, delivery mode (home or relay point), preferred date not earlier than 2026-11-01.
  • Payment: method (cash on delivery, Edahabia, CIB) and an optional comment limited to 200 characters.






EX 03
Business validation rules
Intermediate


Write a supplier account form enforcing, with native validation only:


  • Company name: required, 3 to 60 characters.
  • Mobile phone: Algerian format (10 digits, starting with 05, 06 or 07).
  • Postal code: exactly 5 digits, numeric keyboard on mobile.
  • Annual turnover: a number of at least 0 in steps of 1000.
  • Website: a valid URL, optional.
  • Password: at least 8 characters including at least one digit, with a visible hint linked via aria-describedby.
